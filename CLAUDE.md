# Foundry — a Project Alice fork for the Rise of Nations Vic2 mod

This file exists so a fresh Claude Code session (any machine) can pick up this project with full context. It's the durable record — treat it as more authoritative than any prior conversation, and update it whenever a major decision or convention changes. This mirrors the sister project's own convention — see `../Rise-of-Nations/CLAUDE.md`.

## What this is

A personal fork of [schombert/Project-Alice](https://github.com/schombert/Project-Alice) (an open-source C++ reimplementation of the Victoria 2 engine, GPL-3.0, itself a continuation of the Open V2 codebase), forked to `github.com/Buntcake14/Foundry` on 2026-08-07 and cloned locally to `/run/media/seth/Games/Projects/Foundry` (sibling to `../Rise-of-Nations/`, the actual mod content repo — kept as two fully separate repos on purpose, see "Why two repos" below).

**Fork-only, main branch only.** Upstream (`schombert/Project-Alice`) had only two other branches at fork time (`eriks_branch`, `experimental-map-text`) — both read as in-progress/experimental, not needed as a baseline. They're still fetchable from upstream later if that changes.

## Why this exists

The Rise of Nations mod (`../Rise-of-Nations/`) spent a long time pushing vanilla Victoria 2's closed engine to its limits — see that repo's own CLAUDE.md for the full history (a mesh-builder crash from a hardcoded province-corner buffer, a hardcoded 23-frame unit icon strip that crashes the military screen if exceeded, no live effect to force-construct a building anywhere except a country's capital state, no documented `on_state_conquest` scope, `common/buildings.txt` factory entries having no trigger/condition field at all, a fixed-size GUI background texture that had to be manually stretched twice). Each of those got worked around, not fixed, because the original engine is closed-source.

The concrete trigger was a specific feature: the mod's "Government Administration" building system (`../Rise-of-Nations/events/Government Administration.txt`, `decisions/Government Administration AI.txt`, `common/buildings.txt`/`common/production_types.txt`) — a 4-tier administrative-building chain implemented as a real `type = factory` building (Vic2 has no other extensible building type) whose actual buff is delivered separately via province modifiers synced through an event, because vanilla Vic2 has no conditional/trigger field on factory buildings and no way to force-construct one outside the AI's own workaround (a decision that grants the modifier with **no physical building at all** — see that repo's CLAUDE.md "Government buildings" section for the full reasoning and known asymmetries this caused, e.g. conquering AI land gives you the stat bonus with nothing to see in the production UI, since the AI's path never builds anything real).

Since this is **single-player, for personal use only** (not something being distributed to other players), the usual reasons to stay inside vanilla's constraints (mod portability, requiring players to install a custom engine build) don't apply. Project Alice already ships real Linux support (see "Build" below) and loads Victoria 2's actual game/mod files directly, so the plan is: get Foundry building and running the existing Rise of Nations mod unmodified first, then start extending the engine itself for features vanilla Vic2's script language can't express.

## Why two repos, not one

`../Rise-of-Nations/` (the mod's Paradox-script content: provinces, events, decisions, common/, history/, etc.) is kept completely separate from this engine fork, deliberately, so that **if Foundry work goes badly wrong, the mod keeps working standalone in vanilla/base Victoria 2 exactly as it does today.** Nothing in this repo touches that one.

**Superseded plan (2026-08-07): not mod-loading.** The original intent below this line described Foundry loading Rise of Nations the normal Vic2 way, as a mod via the `mod/` folder. That's been dropped in favor of a **bundled standalone copy**: take a full copy of the vanilla Victoria 2 game files, merge Rise of Nations' content on top (same override semantics the mod's own `replace_path` list already uses — see `../Rise-of-Nations/CLAUDE.md`'s "`.mod` file is install-local" section), and point Foundry at that merged copy as its own self-contained game directory — "our own version." The real Steam Victoria 2 install stays completely untouched/vanilla throughout, playable normally outside of Foundry. Not yet implemented — no merge/bundle script exists yet, and this machine's `mod/Rise of Nations/` (vendored into this repo, script content tracked / `gfx`+`map` gitignored — see git history) was an earlier step toward the old mod-loading plan; it may still be useful as the source content to merge in once the bundling script exists, but nothing currently consumes it that way.

Original mod-loading framing, kept for history: the long-term intent was for Foundry to eventually load that mod's content directly, same as Project Alice loads any other Vic2 mod — not to fork or duplicate the mod's content into this repo.

## Two target features driving this (design intent, not yet implemented)

1. **A "real" government administration system** — replace the mod's province-modifier-riding-a-fake-factory workaround with an actual first-class mechanic, once we have source access to make administration a real conditional/triggered building type instead of an always-buildable factory with a companion event.
2. **One urban center per state** — restrict each state to a single designated village/town/city province where all factories *and* admin buildings can exist, simulating a real urban core instead of Vic2's status quo (the engine already silently assigns factories to some arbitrary province within a state; nothing currently makes that explicit or meaningful, and it undercuts this mod's whole "deliberately split states as a permanent reason for border wars" design philosophy — see `../Rise-of-Nations/CLAUDE.md`'s "Breakup philosophy" — since a building's benefit can currently leak across a split state via `state_scope = { has_building = X }` aggregating the whole geographic state regardless of which owner actually holds the building's province).

**Both ideas turned out to already have a real foothold in Project Alice's source**, found 2026-08-07 while first exploring the codebase — this is the concrete starting point, not a from-scratch build:

- **`src/economy/economy_government.cpp`/`.hpp`** — NOT building-placement code. It's a fully simulated tax/administration economy: `tax_collection_rate`, `count_active_administrations`, separate `capital_administration` vs `local_administration` "control production" functions, real `employment_record`s for people staffing local vs. capital administration. Project Alice has already replaced vanilla Vic2's flat `tax_efficiency` stat with administration modeled as real simulated labor.
- **`src/economy/advanced_province_buildings.cpp`/`.hpp`** — defines three "advanced province buildings": `schools_and_universities`, `civilian_ports`, and **`local_cities_and_towns`** (internal comment: `// cities`). The last one already models urban housing capacity per province — construction cost/build time tied to `province_building_type::railroad`'s costs, size growing or decaying based on profitability and labor, maintenance with decay if unmaintained (`services::list::urban_housing`, `economy::labor::basic_education` as its throughput labor type, `.requires_labor = false` since construction/maintenance itself is what consumes labor here, not ongoing output labor). This is most of the way to the urban-center idea already, just not yet gating factory/admin placement to a single such province per state.
- **The file's own header comment, from the actual maintainer**: *"Advanced province buildings are a future replacement for province buildings... Currently they are hardcoded as 'enums with properties'. Future work should be directed toward moving their definitions into content files and integration with dcon."* — a standing invitation to do close to exactly what both target features need: take this out of hardcoded C++ enums (`services::list::*` / `advanced_province_buildings::list::*`) and make it a real moddable content type, at which point our own admin-tier buildings and a real one-city-per-state gate become natural additions to an existing system rather than something bolted on.

**Update 2026-08-07 (evening session): real implementation started.** See "Civic buildings system" below for the full build — a new, content-file-driven `civic_building_type` engine feature now exists, with `urban_center` as its first real building (gates factory construction, cuts into RGO potential by tier) and RGO leveling turned out to already exist in Alice's economy simulation, now government-reform-gated. This section's original framing (extend `advanced_province_buildings`) was **not** the path taken — a new, separate, moddable-from-content-files system was built instead, per the user's explicit preference to move away from hardcoded C++ definitions (see that section for why).

## Build

**Before doing any build step on a machine (new or otherwise), check what's already installed rather than assuming — this file describes what was true on the machine it was last updated from, not necessarily the one you're on now:**
```
which cmake clang clang++ && cmake --version && clang++ --version
```
If any are missing, install the apt deps below first. If a `build/` directory already exists, check whether it was configured with clang (see the compiler pitfall note below) before building — don't assume a prior session got it right.

**Confirmed real native Linux support** (not just a Windows binary run through Proton/Wine) — `src/entry_point_nix.cpp` exists alongside `entry_point_win.cpp`, and upstream ships a GitHub Actions AppImage build. CI (`.github/workflows/appimage.yml`) validates against **clang-20 on Ubuntu 24.04**; this machine (Ubuntu 26.04) has **clang 21.1.8** (`llvm-21`) and **cmake 4.2.3** via apt — both newer than CI's baseline, and no issues surfaced from that gap.

Debian/Ubuntu build deps (matches both `docs/contributing.md` and the actual CI workflow):
```
sudo apt update
sudo apt install git build-essential clang cmake libgl1-mesa-dev libxrandr-dev libxinerama-dev libxcursor-dev libxi-dev libicu-dev
```

**Known gotcha, already satisfied by this clone's location**: the bundled Intel TBB library fails to compile if the project's own path contains any spaces. `/run/media/seth/Games/Projects/Foundry` has none. (Victoria 2's own install path *does* have a space — `.../steamapps/common/Victoria 2` — but that's irrelevant to this gotcha, which is specifically about Foundry's own source path, not the game install it points at.)

**Compiler pitfall (hit and fixed 2026-08-07)**: plain `cmake -B build .` picks up the system default `cc`/`c++`, which on this machine resolve to **GCC 15**, not clang, even with clang installed side by side. The project passes clang-specific flags (e.g. `-ffp-model=precise`), so a GCC-configured build fails partway through with `unrecognized command-line option`. Always configure explicitly:
```
cmake -B build . -DCMAKE_BUILD_TYPE=Debug -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++
```
If a build was already configured with the wrong compiler, `rm -rf build` and reconfigure — switching `CMAKE_C_COMPILER`/`CMAKE_CXX_COMPILER` on an existing cache doesn't reliably take.

Build commands (from `docs/contributing.md`, "Linux (Generic)" section):
```
cmake --build build --parallel --target launch_alice   # the launcher
cmake --build build --parallel --target Alice          # the main game (full rebuild every time)
cmake --build build --parallel --target AliceIncremental  # same, but split into smaller translation units for fast iterative rebuilds — prefer this one day-to-day
```
`SaveEditor` is Windows-only per the docs, skip it. The full `Alice` target combines nearly all source into one translation unit — a single-line change can mean a ~10 minute rebuild — so use `AliceIncremental` for actual development; GitHub CI builds the plain `Alice` target, so that's still worth doing at least once before considering something done, to catch anything that only breaks under the combined build. Both `AliceIncremental` and `launch_alice` build clean with only harmless warnings (`-Wnontrivial-memcall` in `serialization.hpp`, a `-Wformat-security` in the nix launcher) — no errors.

**`launch_alice` and the game binary must be rebuilt together after any dcon-schema or hand-serialized-struct change (found 2026-08-07).** `launch_alice` builds a mod's scenario `.bin` by calling into the same `load_scenario_data`/serialization code the game itself links — if `launch_alice` is stale relative to the game binary, it writes a scenario file in an *old* binary layout while the game reads it back expecting the *current* one. Everything after the first mismatched struct (memcpy'd hand-written fields like `parsing::defines`/`economy::global_economy_state` are especially exposed, since those are raw `sizeof()` copies, not self-describing) silently misaligns, and the game segfaults deep in `memcpy`/`deserialize<T>` with a garbage huge length — confusingly, `-test` mode on the game binary alone won't catch this, since it builds and reads the scenario in the same process with one binary, never exercising the cross-binary mismatch. **After any change to `src/gamestate/dcon_generated.txt` or any hand-written section in `serialization.cpp`, rebuild both `AliceIncremental` (or `Alice`) *and* `launch_alice`, then clear `~/.local/share/Alice/scenarios/*.bin`** (stale cached scenarios don't auto-invalidate on a schema change) before testing — don't assume rebuilding just the game target is enough.

**Corollary, hit for real 2026-08-09 during the economy milestone-1 RGO fix**: this isn't only a schema-mismatch/crash risk — `launch_alice` is *also* the binary that actually runs scenario generation whenever a game is started normally through the GUI (not just `-test`), because it links and calls the same scenario-building code (e.g. `economy.cpp`'s initial-RGO-distribution logic) as the game binary. If `launch_alice` is stale relative to a change in *any* scenario-generation logic — not just schema/serialization — it will keep silently generating scenarios with the **old** behavior no matter how thoroughly `~/.local/share/Alice/scenarios/*.bin` gets cleared, since the stale binary just regenerates stale data into a fresh-looking file. No crash, no error — the fix just looks like it didn't work. **Practical rule: after touching any code that runs during scenario creation, rebuild `launch_alice` too, every time, even for a plain logic tweak with no schema change involved** — check both binaries' mtimes if a fix appears not to have taken effect after a full cache clear.

**Runtime linking gotcha**: the built binaries (`build/AliceIncremental`, `build/Launcher/launch_alice`) dynamically link against LuaJIT, but the fetched LuaJIT build only installs its `.so` under `build/dependencies/luajit/luajit-prefix/lib/`, which isn't on the default loader path. Running either binary needs:
```
export LD_LIBRARY_PATH=<repo>/build/dependencies/luajit/luajit-prefix/lib:$LD_LIBRARY_PATH
```
or the binary fails immediately with `error while loading shared libraries: libluajit-5.1.so.2: cannot open shared object file`.

**"Final touches" step — done 2026-08-07**: Alice needs to find Victoria 2's actual game files (graphics, etc.) to run, via its working directory at launch. This machine's Victoria 2 install is at `/run/media/seth/Games/SteamLibrary/steamapps/common/Victoria 2/`. **Correction to an earlier claim in this file**: nothing is actually symlinked into that install's `mod/` folder — it contains only Paradox's own placeholder `dummy.txt`, not a `Rise of Nations` symlink. That still needs to be set up whenever mod-loading work actually starts; it doesn't block vanilla-Alice from building or running. **Superseded by the bundled-copy plan above (2026-08-07)** — a `mod/` symlink into the real Steam install is the old mod-loading approach; the current plan runs Foundry against a separate merged copy instead, leaving the real install's `mod/` folder alone entirely.

The docs say "copy the assets folder to your V2 directory" — read literally, that means the copy must land as `<V2 dir>/assets/`, preserving the folder itself, because engine code opens paths like `assets/fonts/LibreCaslonText-Regular.ttf` *relative to the V2 root*. (First attempt here merged the folder's *contents* straight into the V2 root instead, which builds/launches without error but segfaults on the first text render — `hb_ft_face_create` on a null font buffer — because `assets/fonts/...` didn't resolve. Fixed by re-copying so the `assets/` folder itself sits under the V2 root.) Confirmed working: with `LD_LIBRARY_PATH` set as above and cwd set to the V2 directory, `build/Launcher/launch_alice` opens and renders its full UI correctly (mod list, Create Scenario, Singleplayer/Multiplayer panels) — verified visually via screenshot.

No IDE launch-configuration (`launch.json`/CMake debug config) has been set up yet to make this automatic; for now, running from a shell with the working directory and `LD_LIBRARY_PATH` set as described above is the way to launch.

## Strategic pivot: roll back to vanilla Vic2, then expand our own way (planned 2026-08-08, not yet started)

**The decision.** The user knows vanilla Victoria 2 deeply and doesn't want to have to reverse-engineer years of Project Alice's own accumulated redesign (economy, military, population/rebellion) before they can build their own systems on top with confidence. After investigating whether a shortcut exists (a built-in "classic mode" toggle, or an old git tag close to vanilla-faithful), the answer came back no on both counts — see the reasoning below — so the actual plan is: **keep Alice's engine/plumbing (dcon containers, parsers, rendering, UI framework, build system, AI) and the one Alice redesign the user explicitly wants to keep (the per-state market/trade-route economy), but rewrite each simulation system's actual game-design rules back toward vanilla behavior, one system at a time**, using the user's own vanilla knowledge as the source of truth for exact formulas, and Alice's current code only as a reference for engine-integration patterns when building something similar later. Four systems need this treatment: **economy, military, population/rebellion, diplomacy/politics** — user chose to start with **economy** first despite it being the highest-risk/most-entangled, since it's foundational to everything else.

**Why there's no shortcut (investigated, not assumed).** No `simulation_mode`-style toggle exists anywhere (the only real runtime toggle of this kind is `sys::projection_mode`, and it's scoped purely to map rendering — a one-off, not a pattern). Alice's own founding doc (`docs/about.md`) states the original intent was "imitate Victoria 2 mechanics extremely closely... until 1.0, then a playground for experiments" (v1.0.0 tagged 2023-12-28) — but even the pre-1.0 economy design doc (`docs/economy_design.md`, March 2023) already documents deliberate deviations from vanilla's literal purchase-order resolution, so a literal vanilla baseline never existed in Alice's history, even at the start. The state-market/trade-route system landed later still, in `v1.2.0` (Dec 2024, starting from commit `cd35d8393`) — so `v1.1.4` is the last tag before that specific rewrite, but checking it out doesn't give a modular "vanilla base with a slot for state markets": it's an older, unmaintained codebase *without* state markets at all, meaning the user would have to hand-rebuild that system from scratch on top of it — more work than the comb-through-Alice's-code problem this plan exists to avoid. Rolling back git history was rejected for this reason.

**AI is a special, unfixable case.** Victoria 2's actual AI was never open-sourced, so there is no vanilla AI to revert to — Alice's AI (`src/ai/`, ~6,900 lines across 17 files: `ai.cpp`, `ai_war.cpp`, `ai_economy.cpp`, `ai_alliances.cpp`, `ai_influence.cpp`, `ai_campaign*.cpp`) is necessarily original engineering. Good news: it's cleanly modular by domain, so the plan is to **leave AI code as-is** and treat each simulation-system rewrite's AI call sites as a per-milestone integration check (re-verify thresholds/semantics still make sense against the new formulas) rather than a separate AI-rewrite phase.

**Reconsideration and confirmation (2026-08-09).** Mid-way through starting this phase, the user briefly reconsidered milestone 1 specifically (single RGO per province) and decided against it, on the grounds that Alice's per-state trade-route network makes cutting secondary RGOs a real scarcity risk vanilla's global pool never had (no fallback if a nation's trade connectivity is poor). After sleeping on it, the user reversed that reversal the same week: the full six-milestone plan is back on as originally written below, including milestone 1, accepting that risk deliberately. **Scope was also widened the same day**: alongside the four simulation systems below, the user decided to vanilla-ify Foundry's **GUI** too, canceling the separate custom-AI-art UI initiative that State Ledger (see below) was step one of. Any window Alice's own developers changed away from vanilla Vic2's actual layout/behavior is now in scope to revert, and previously-built custom-art windows (State Ledger) should eventually be reskinned toward vanilla's actual assets/style rather than extended with more AI art. No milestone plan for the GUI pass exists yet — economy remains the active phase.

**Economy phase — the concrete plan, milestone by milestone.** Investigation found wages already clear **per-province** (not per-state), using the same smoothing-primitive family as goods pricing (`economy.cpp` ~4394-4442) — this means the "necessary plumbing to keep" for state markets is narrower than initially feared, and most of what needs reverting is actually separable from it. No dcon schema changes are expected for any of the six milestones below (all target fields are already generic enough), which sidesteps the rebuild-both-targets-and-clear-cache gotcha for this entire phase unless a milestone note says otherwise. Standard verification loop for every milestone: `cmake --build build --parallel --target AliceIncremental`, then `build/AliceIncremental --mod "mod/Rise of Nations.mod" -test`, then a real play session via `launch.sh`.

1. **Single RGO per province — done 2026-08-09.** `src/economy/economy.cpp` ~823 gave a province a slot for its `main_rgo` *and* any other commodity whose `actual_size` cleared `state.defines.alice_secondary_rgos_min_employment`. Condition tightened to `main_rgo == c` only. No AI coupling found.

   **Follow-up, same day**: after the fix, every province was still showing an extra RGO for the mod's designated "money" good (`precious_metal` in Rise of Nations — whichever commodity has `money = yes` in `goods.txt` gets aliased onto `economy::money`/commodity slot 0 by `parsers_declarations.cpp`'s `good::money` handler, copying its properties in and popping the original slot). This is because of a **second, separate mechanism**: `economy.cpp`'s scenario-generation loop unconditionally added a flat trickle of that money commodity to *every* province (previously lines 839-843, right after the per-commodity loop), as an Alice-only inflation source with no vanilla equivalent — the milestone 1 plan originally flagged this and deliberately deferred it ("it never competes for labor, it's a judgment call for later"). User decided to remove it outright as part of the full vanilla revert; the block is now deleted. **Open question for a future milestone**: vanilla Vic2 gets its inflation/liquidity behavior from other mechanics (tax/trade dynamics), not a per-province trickle — worth confirming nothing downstream (e.g. `economy_trade_routes.cpp`'s money-commodity-specific logic) assumed every province always had a nonzero `money` RGO stockpile.

   **Reusable lesson**: `launch_alice` is the binary that actually performs scenario generation when starting a game through the normal GUI flow (not just `-test`), because it links the same scenario-building code as the game binary. It must be rebuilt after *any* change to scenario-generation logic, not just dcon-schema/serialization changes — see the "Runtime linking gotcha"/rebuild-together section above, which now documents this broadened corollary in full. A stale `launch_alice` silently keeps generating old-behavior scenarios into freshly-cleared cache files, which is confusing to debug (looks like the cache-clear didn't work, when actually the *generator* itself was stale).
2. **Vanilla-style factory throughput/output.** `economy_production.cpp` — remove `factory_throughput_multiplier`'s (~981-1007) Alice-only urbanization-penalty and size-scaling terms, and remove the "secondary worker" bonus-output concept (`output_multiplier_from_workers_with_high_education`/`high_education_power`, ~398-419) by folding to `1.0f`. AI coupling: `ai_economy.cpp`'s `factory_total_employment_score` upgrade-eligibility threshold (`>= 0.9f`) should be re-sanity-checked once Milestone 6 changes employment dynamics.
3. **Remove subsistence-farming pseudo-employment** (sequenced *before* Milestone 4 on purpose — it injects a "free consumption" term into the same function Milestone 4 needs to rewrite, so removing it first avoids touching those lines twice). `economy.cpp` ~963-1153 (`subsistence_size`, `update_local_subsistence_factor`, the `subsistence_employment` accumulation in `update_pops_employment`) and `economy_pops.cpp` ~114-237 (`adjusted_subsistence_score` and its use in `prepare_pop_budget_templated`) — an unemployed pop should just be unemployed and poor, like vanilla. No AI coupling found.
4. **Strict tiered needs consumption.** `economy.cpp` ~175-307 (`rebalance_needs_weights`, called daily per market at ~4364) — remove the dynamic reweighting engine, use fixed per-pop-type need weights. `economy_pops.cpp`'s `prepare_pop_budget_templated` (~124-446) currently computes life/everyday/luxury spending ratios *simultaneously*; rewrite so everyday-needs spending is gated behind life-needs hitting ~100% satisfaction, and luxury behind everyday hitting ~100% — vanilla's hard on/off tier gate instead of continuous reweighting. No direct AI coupling; downstream pop-satisfaction consumers (militancy/consciousness/migration triggers, several GUI windows) just consume a float, no code changes needed there, but expect more step-like displayed values.
5. **Discrete-style artisan production.** `economy.cpp`'s `initialize_artisan_distribution` (~160-173) currently seeds every commodity's `artisan_score` simultaneously — seed one good per province instead. `economy_production.cpp`'s daily artisan-score update loop (~2340-2405, continuous gradient smoothing) should become a periodic "compare current good's profit to a candidate, wholesale-switch if the candidate wins" reroll pattern instead of blending every commodity daily. True per-pop-object good assignment (vs. province-aggregate) would need a new dcon field — deferred as an optional stretch goal since it triggers the schema-change rebuild gotcha. No AI coupling found.
6. **Labor market: vanilla priority-based hiring on top of the necessary wage clearing** (highest-entanglement, done last on purpose). Today, when labor is scarce, `economy.cpp` ~3175-3191 computes one shared `labor_demand_satisfaction` scalar per province/tier applied equally to every employer — pure proportional rationing, no priority order at all. The unused hook: `factory_priority`/`set_factory_priority` (`economy.cpp` ~999-1005) already exists with real vanilla-style priority-arrow UI in the factory panel, currently only consulted by automatic-investment ranking, never by hiring. Recommended approach: keep wage clearing untouched; replace the shared scalar with a per-factory, priority-ordered allocation (sort by `factory_priority` then profitability, consume available `labor_supply` until exhausted, computed fresh each tick — no schema change); replace factories' continuous profit-gradient "desired workforce" walk (`economy_production.cpp` ~1909-2066, ~2068-2433) with vanilla's more direct "wants full `base_workforce * level`" rule plus light damping. RGO/artisan employment stay out of this priority queue (vanilla drives their participation by profitability, not a hiring queue). **Needs the user's vanilla knowledge before/during implementation**: the exact tiebreak rule for equal-priority factories. AI coupling: `ai_economy.cpp` reads `province_get_labor_price` (unaffected) and two coarse-aggregate threshold checks (`labor_supply_sold <= 0.95f`, `labor_supply > 5000.f`) that should keep working if the coarse aggregate is kept computed alongside the new per-factory pass.

**After economy** (scoped only lightly so far, real milestone planning happens when their turn comes): **military** has several self-contained divergences already identified — naval evasion is a flat damage-reduction multiplier instead of vanilla's hit-chance roll (`military.cpp` ~7951-8061), a non-vanilla naval stacking-damage-penalty/coordination-bonus formula, a split war-exhaustion multiplier for attrition vs. combat losses, and a new "reserve battle-line" mechanic not in vanilla's simpler frontline/backline model (deepest-wired item found in military). Fort/siege formulas are mostly vanilla-faithful with a couple of Alice-only scaling knobs layered on — worth numerically re-verifying rather than assuming divergence. **Population/rebellion**: pop growth already tracks vanilla's formula closely (low effort); rebellion/rebel-faction mechanics were a deliberate target of Alice's own post-1.0 redesign (per their devlogs, motivated by "rebel spam") and need a closer audit against vanilla's militancy-based system. **Diplomacy/politics**: least explored so far — elections/reforms look structurally vanilla-shaped, but crisis/sphere-of-influence/casus-belli mechanics need a dedicated investigation pass before they can be scoped concretely.

**Verification of the overall approach**: beyond each milestone's own in-game checks, run a longer `-test` session (several in-game years) after all six economy milestones to confirm the economy is stable end-to-end (no runaway unemployment, price spirals, or AI economic collapse) before calling the economy phase done and moving to military.

## Civic buildings system (implemented 2026-08-07)

A real, content-file-driven engine feature — the user's explicit design goal was buildings/tiers/requirements/buffs defined in **moddable text files** (like `buildings.txt`/`event_modifiers.txt` already are), not hardcoded C++ structs, specifically so future buildings can be added/tuned from the Rise of Nations repo alone, without a Foundry rebuild. Confirmed working end-to-end: compiles clean, and a real scenario build (`AliceIncremental --mod "mod/Rise of Nations.mod" -test`) parses the new content with zero errors and boots into a running game.

**Origin story, condensed**: started from "urban centers that level up automatically based on requirements (pop growth), gate factory/admin building placement, and eat into local RGO output" plus "RGO leveling gated by government type." Investigation found Alice already has most of the RGO half built (see below) — the actual new work was the generic leveling framework and urban centers specifically.

**Data model** — new dcon object `civic_building_type` (`src/gamestate/dcon_generated.txt`), a scenario-loaded registry (like `factory_type`) with `name`, `level_count`, `is_urban_center`, `is_rgo_level` flags, and `levels`: a fixed `std::array<civic_buildings::level_definition, 8>` (struct defined in new file `src/economy/civic_buildings.hpp`) holding per-level `requirement` (`dcon::trigger_key`), `modifier` (`dcon::modifier_id`, reusing the normal `event_modifiers.txt` system), `cost` (`economy::commodity_set`), `construction_time`, `rgo_output_penalty`, and `unlocks_factories`/`unlocks_admin_buildings` flags (urban-center-specific). Per-province state: two new resizable arrays on `province`, `civic_building_level` (`uint8_t` per type) and `civic_building_progress` (`float` per type), sized at scenario-build time via `civic_buildings::initialize_size_of_dcon_arrays`.

**dcon-schema gotcha found while building this**: template types with a comma in them (`std::array<T,N>`) must **not** have a space after the comma in the schema `type{...}` field — `std::array<T, N>` silently breaks the code generator's naive text substitution (produces garbage like `std::array<T,)` in the output), while `std::array<T,N>` works. Existing schema entries already follow this convention; easy to miss when writing a new one by hand.

**New trigger condition**: `province_population_growth` (fraction, e.g. `0.02` = 2%), computed from a new `population_year_ago` float snapshotted on every province at the yearly tick (`system_state.cpp`'s `ymd_date.month == 1` block) and compared against current population. **Adding one new trigger condition touched 5 files**: `trigger_parser_defs.txt` (grammar), `script_constants.hpp` (bytecode opcode — note `first_scope_code` must be bumped when adding an opcode, or the new one silently collides with the first scope code), `trigger_parsing.hpp` (script-file parser callback), `triggers.cpp` (the real evaluator), and — unexpectedly — `fif_triggers.cpp` (a second, currently-**dead-code** Forth-like "fif" bridge that still must compile a matching case for every opcode even though nothing calls `fif_trigger::evaluate` anywhere in the codebase yet). **Conclusion for future buildings**: reuse existing trigger conditions (`has_building`, tech/literacy/pop checks, etc.) wherever possible — inventing a new one is expensive, existing content-file work is not.

**Parser**: new `civic_buildings.txt` top-level content file (grammar in `parser_defs.txt`, structs in `parsers_declarations.hpp`, implementation in new file `src/parsing/civic_buildings_parsing.cpp`, wired into `parsers.cpp`'s include chain). Loaded in `system_state.cpp`'s `load_scenario_data` **after** `event_modifiers.txt` specifically — a level's `modifier` field resolves against `map_of_modifiers`, which only exists once that file has parsed; got this ordering wrong on the first pass (civic_buildings.txt was originally placed right after `buildings.txt`, well before `event_modifiers.txt`) and had to move it.

**Runtime** (`src/economy/civic_buildings.cpp`): `update_leveling` runs daily (hooked into `economy.cpp`'s main tick, right after `advanced_province_buildings::update_consumption`) — for each province/civic-building-type pair below max level, evaluates the next level's `requirement` trigger; if met, accumulates `civic_building_progress` by `1/construction_time` per day; on completion, bumps the level and swaps the active province modifier (`sys::remove_modifier_from_province`/`add_modifier_to_province` — the same real engine calls `add_province_modifier`/`remove_province_modifier` script effects use, so no country_event workaround needed, unlike the mod's old Government Administration building).

**Urban-center-specific hooks** (only active when `is_urban_center` is set on a type):
- `civic_buildings::province_unlocks_factories`/`province_unlocks_admin_buildings` — true once any level up to and including the province's current level has that flag set. Wired into `commands.cpp`'s `can_begin_factory_building_construction`: **new factory construction now requires an urban center to have unlocked it in that specific province** — applies mod-wide immediately, including to provinces with no urban center yet, so expect factory construction to be broadly blocked until urban centers get built up.
- `civic_buildings::province_urban_rgo_penalty` — cumulative penalty from the current level, applied as a multiplier on `rgo_potential` (the ceiling), not `rgo_size` (the current value) directly, inside `economy_production.cpp`'s real RGO investment/growth loop — so a province's RGO decays toward the new lower cap gradually via the loop's own existing clamp, not instantly.

**RGO leveling — turned out to already exist.** Alice's real economy already grows `rgo_size` toward `rgo_potential` continuously, funded by a nation's private-investment pool, based on real profitability (`economy_production.cpp`, the `local_investment`/`rgo_investment_tokens` machinery) — this **is** RGO leveling, just not previously gated. Added one line: automatic private-investment-funded growth now checks `issue_rule::can_invest_in_pop_projects` (a reform-option bit that was already parsed from `common/issues.txt`/`common/reforms.txt` but never read anywhere in the engine) on the owning nation first. Matches the design exactly: player can always manually invest (once the manual command below exists), but automatic/passive growth goes quiet under a government whose reforms don't grant that bit.

**Removed**: the pre-existing per-province "toggle local administration" button (`gui_province_window.cpp`'s `province_toggle_administration_button`, next to "Change Capital") — swapped for `invisible_element` since it's a player-facing way to create competing "administrative regions," conceptually overlapping the new urban-center/admin-building system. The underlying simulation (`economy_government.cpp`'s real administration/tax/employment logic) is untouched; only the player's manual UI control was removed.

**Deliberately deferred** (not built, tracked as known gaps, not urgent):
- A real player-manual "invest in this RGO anyway" command + GUI button, bypassing the investment-reform gate — needs a new `command_type`, serialization, and a `can_/begin_` pair (same shape as `commands.cpp`'s factory-construction functions).
- A remove/demolish command for civic buildings (levels currently only ever go up).
- A `has_civic_building` trigger, so one civic building can require another's presence directly — would let buildings gate each other (the actual eventual ask), same 5-file cost as `province_population_growth` above. The one real content file written so far (`../Rise-of-Nations/common/civic_buildings.txt`) has a placeholder: `sanitation_office` requires `literacy = 0.30` instead of "requires an urban center," specifically because this trigger doesn't exist yet.
- Real terrain-type differentiation for farm/mine RGO output (mountain currently scores identically to plains) — a data-tuning task in `../Rise-of-Nations/map/terrain.txt`, not an engine change; a full proposed value table was written up in conversation but never applied to the file. Revisit before considering the "RGO capped by terrain" part of the original ask done.

**Content so far**: `../Rise-of-Nations/common/civic_buildings.txt` (`urban_center`, 4 levels; `sanitation_office`, 1 level) plus 5 new modifiers in `../Rise-of-Nations/common/event_modifiers.txt` (`urban_center_hamlet_bonus`/`_town_bonus`/`_city_bonus`/`_metropolis_bonus`, `sanitation_office_bonus`).

## State Ledger window (implemented and working, fixed 2026-08-08)

A new standalone topbar window (explicitly **not** nested in the vanilla Ledger — first version was, user asked to pull it out into its own dedicated button/window instead) listing the player's own states with three at-a-glance health signals — life-needs satisfaction, market balance (state's market money stockpile), RGO utilization (`rgo_size`/`rgo_potential` across all goods) — plus a "View" button per row that jumps to that state's capital and opens its market tab. Intended as the future entry point into a planned Economy Viewer rework (see below) — user's words: *"I want all the [data] at my fingertips just not the way Alice presents it."*

**Files**: new `src/gui/gui_state_ledger_window.hpp` (window + listbox + row + cell classes), `.gui` additions in `assets/alice.gui` (`state_ledger_window` windowType, `state_ledger_row` — a **custom** row template, deliberately not reusing vanilla's `default_listbox_entry` since that's hardcoded to 972px wide and this window is 800px) and `assets/alice_menubar.gui` (`state_ledger_button`), plus the usual `ui_state.hpp` pointer + `gui_minimap.hpp` button class + name dispatch. `province_subtab_toggle_signal` enum had to be moved from `gui_province_window.cpp` into `gui_province_window.hpp` to make it visible to the new file (needed for the "View" button's jump-to-market behavior).

**Bug #1 (found and fixed 2026-08-07)**: the listbox's placeholder area was declared as `instantTextBoxType` in the `.gui`, which doesn't honor a generic `size` field the way a real container does — `listbox_element_base::on_create()` (`gui_listbox_templates.hpp`) pre-allocates its pool of row elements based on `base_data.size.y`, so a listbox that inherits a wrong/zero size never creates any row objects at all, regardless of how much data is in `row_contents`. Fixed by changing it to `listboxType` (matching vanilla's own `default_listbox`, which uses `listboxType` with `scrollbartype`/`spacing`/`borderSize` fields).

**Bug #2 (found and fixed 2026-08-08)**: after fix #1, the window opened with the correct number of row slots, but every row stayed empty until the player happened to visit another window (e.g. the vanilla Ledger) and come back. Root cause: `listbox_element_base<RowWinT,RowConT>::on_create()` only calls the base `update(state)` at the end (which maps existing `row_contents` into row widgets) — it never calls the derived `on_update(state)` override (`state_ledger_listbox::on_update`, which is what actually populates `row_contents` from `state.world.nation_for_each_state_ownership(...)`). That override only runs as part of `ui_state.root->impl_on_update(state)`, which the engine calls automatically, but *only* when `sys::state::game_state_updated` flips true — i.e. on the next simulation tick, not synchronously on window creation. So a freshly opened window sits empty until the ambient game clock happens to tick, which is exactly why switching to the vanilla Ledger and back "fixed" it (real time passed, a tick fired, the deferred update finally ran) — the vanilla Ledger has the same latent behavior, just usually masked because a tick happens before anyone notices. **Fix**: `minimap_state_ledger_button::button_action` (`gui_minimap.hpp`) now explicitly calls `state.ui_state.state_ledger_window->impl_on_update(state)` right after creating the window and right after re-showing it — the same explicit-refresh pattern already used by `minimap_mapmode_button::button_action` for its own UI-only (non-gamestate) change. Confirmed working in-game: states populate immediately on first open. **General lesson for any future from-scratch window with a listbox**: don't assume `on_create` populates data — either force an `impl_on_update` right after creation (this fix's approach) or have the listbox's own `on_create` call its `on_update` override directly instead of relying on ambient ticks.

## GUI/asset debugging lessons (found 2026-08-07 — read before touching `.gui`/`.gfx`/localisation again)

A single new topbar button took an extremely long time to even become visible, for five separate, stacked reasons — worth internalizing all five so the next UI change doesn't repeat this:

1. **Foundry reads assets from the live Victoria 2 install directory, not the repo.** Every `.gui`/`.gfx`/localisation edit needs `rsync`-ing (or equivalent) to `<V2 dir>/assets/` before it's visible in-game — the repo's own `assets/` folder is just the source of truth, not what the running game actually reads. Forgetting this re-sync looks exactly like "my change did nothing."
2. **`Orientation` string values are stricter than they look.** The actual recognized tokens (`src/parsing/gui_graphics_parsers.cpp`) are `center`/`centre`, `lower_left`, `lower_right`, `upper_left`, `upper_right`, `center_up`, `center_down` — **not** `upper_center`/`lower_center`, which read as plausible but are silently rejected (logged into an internal error accumulator that's never surfaced to the user anywhere, so a typo here just looks like the element vanished).
3. **`make_element_by_type<T>(state, "some_name")` fails completely silently** if the string doesn't resolve to a real `.gui` element name — returns an empty/null `unique_ptr<T>`, no error, no crash. Any code creating a window by name string (the lazy-create-on-first-click pattern used throughout `gui_minimap.hpp`) can fail this way with zero diagnostic output.
4. **Rise of Nations has an incomplete mod-wide TGA→DDS conversion.** A large fraction of `gfx/interface/*.tga` files were converted to `.dds` at some point, but several of vanilla's own `.gfx` sprite definitions still reference the old `.tga` filename, which no longer exists in the mod's folder (only the `.dds` version does) — and this engine's sprite loader does **not** automatically retry alternate extensions (confirmed via `src/graphics/texture.cpp`'s `load_file_and_return_handle` call sites — the `.png`→`.tga` fallback that exists there is for a different, specific texture-loading path, not general `.gfx` sprites). The result: the button/window element exists and its logic/keyboard-shortcut fully works, but nothing visible renders — confirmed affected: `GFX_menu` (`menu.tga` missing), `GFX_ledger_button` (`menubar_ledger.tga` missing), `GFX_ledger_bg` (`ledger_bg.tga` missing); confirmed **safe** (already reference `.dds` correctly): `GFX_frontend_button_236`, `GFX_main_close_button`. **Practical consequence: test new UI features in a vanilla (no-mod) scenario first** — it isolates whether new code is actually correct from this entirely separate, pre-existing mod-asset bug, which cost most of a session's debugging time by being conflated with the real feature work. This same gap likely affects other not-yet-noticed vanilla UI while playing this mod and is worth a dedicated pass in `../Rise-of-Nations/` at some point (grep every `.gfx` file's `texturefile` against what's actually present in `gfx/`, matching extension).
5. **Some vanilla sprites are marked `loadType = "FRONTEND"`** (e.g. `GFX_frontend_main_bg`) and are only loaded during the main-menu scene, unloaded during actual gameplay — don't reference these for any in-game (as opposed to main-menu) UI.

Separately: **`listboxType` is a distinct `.gui` element type from `instantTextBoxType`/generic `windowType`**, and must be used for any element whose declared `size` a `listbox_element_base` will inherit to compute its row-pool — see "State Ledger window" above for the concrete bug this caused.
